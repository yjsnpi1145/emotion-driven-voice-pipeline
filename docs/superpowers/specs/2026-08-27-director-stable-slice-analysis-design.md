# 导演分析稳定切片设计

日期：2026-08-27
状态：已通过（用户确认修复）

## 1. 问题

导演模式当前要求 LLM 为每条语句返回绝对 Python 字符下标和完整 `source_text`。实际模型会改写空白、遗漏字符或错误计算中文下标。已复现的响应把实际对应原文 `0:142` 的文本标记为 `0:71`，并将长度为 2398 的分块只覆盖到 1445，最终触发：

```text
analysis source_text does not match the source slice
```

服务端拒绝该结果是正确的，但继续通过提示词要求不同模型精确计算下标不能稳定解决问题。

## 2. 目标

- LLM 不再生成或回传原文字符下标和原文副本。
- 服务端从原始字符串确定所有范围和 `source_text`，保证完整、连续、零改写覆盖。
- LLM 仍负责语句类型、临时角色、别名、置信度和是否配音。
- 保留导演模式既有角色归并、人工复核、翻译、生成及失败恢复行为。
- 已保存的旧格式分析缓存不得被新流程复用。

## 3. 方案比较

### 方案 A：顺序模糊匹配旧响应

根据 LLM 返回文本在原文中做精确或模糊搜索，再重建下标。改动较小，但重复台词、被改写字符和缺失空白会造成歧义，可能把错误角色静默绑定到错误原文，因此不采用。

### 方案 B：校验失败后重复要求模型修正

保留旧 Schema，通过追加提示让模型重新计算下标。实现简单，但仍依赖模型计数能力，会增加延迟、费用和上游限流概率，不能根治，因此只保留现有的用户级重试，不作为修复方案。

### 方案 C：本地稳定切片 ID（采用）

服务端确定性切分原文，为每个连续切片分配稳定 ID。LLM 每个 ID 只返回分类字段，服务端按 ID 将分类结果附加回原始切片。该方案从数据契约中移除模型最不可靠的下标和原文复制任务，并保持严格校验。

## 4. 数据契约

### 4.1 本地分析单元

每个 `ScriptChunk` 在本地继续按句末标点、换行和长度上限切分为连续单元：

```text
unit_id
source_start
source_end
source_text
```

`unit_id` 由分块 ID 和单元序号稳定生成。单元必须首尾相接并完整覆盖所属分块；空白只作为相邻原文的一部分保留，不单独丢弃。

### 4.2 LLM 输出

LLM 对每个输入单元返回且仅返回：

```text
unit_id
kind: dialogue | narration | stage_direction
temporary_role_name
role_aliases
role_confidence
speak_enabled
```

输出不得包含 `source_start`、`source_end` 或 `source_text`。结果必须与输入单元一一对应、顺序一致，不能缺失、重复或包含未知 ID。

### 4.3 服务端物化

服务端验证 ID 后，从本地单元复制原始 `source_start`、`source_end` 和 `source_text`，生成现有 `AnalyzedUtterance`。下游 `ChunkAnalysisResult`、角色归并、SQLite 语句表和 WebUI API 保持不变。

## 5. 切片规则

- 优先在 `。！？.!?；;` 和换行后结束单元。
- 防止无标点长段无限增长，单元长度达到 160 个 Python 字符时强制切分。
- 连续空白附着到下一条非空单元；末尾空白附着到最后一条。
- 全空白分块仍生成一个单元，以保证覆盖；项目层已有非空原文约束。
- 单元 ID 使用固定宽度序号，例如 `<chunk-id>:u0000`，不依赖 LLM 或文本规范化。

## 6. 缓存与兼容性

- 数据库表不变，最终仍缓存 `ChunkAnalysisResult`。
- 分析缓存契约升级到 `director-analysis-units-v2` / Schema 2。
- `load_analysis_chunk` 同时校验 source SHA、LLM fingerprint、prompt version 和 schema version。
- 旧的 `director-analysis-v1` 缓存自动视为未命中，并由新流程重新分析；无需数据库迁移或删除历史项目。
- 导演项目和公开 API 不增加破坏性字段。

## 7. 错误处理

- ID 缺失、重复、乱序或未知时不做模糊匹配。客户端携带原始单元和校验原因进行一次结构化修复请求；第二次仍无效才返回 `LLM_INVALID_RESPONSE`。
- 本地物化后继续执行现有 `validate_chunk_analysis`，作为第二层完整覆盖校验。
- 上游 HTTP 429、503 和网络错误继续走现有网络重试逻辑；本次不混入重试退避策略改造。
- 失败项目保持 `analyzing + last_error`，用户可在 WebUI 使用“重试剧本分析”。

## 8. 测试与验收

1. 单元切分完整保留中文、换行、空白和长段，范围首尾相接。
2. LLM Schema 不再接受原文下标或 `source_text`。
3. 物化使用本地原文，即使分类对象只含 ID，也能得到精确的原文范围。
4. 缺失、重复、乱序和未知 ID 会触发一次结构化修复，第二次仍无效时被拒绝。
5. 使用“返回文本 142 字符但声称范围 71 字符”的回归场景证明新请求根本不要求模型返回这两个字段。
6. 旧 v1 缓存不会被 v2 流程复用，v2 成功缓存仍可恢复。
7. 导演分析、角色归并、翻译和端到端 CPU 测试通过。
8. `ruff`、格式检查、`mypy`、非 GPU 完整测试和 wheel 构建通过。

## 9. 非目标

- 不实现模糊文本对齐。
- 不改变导演 WebUI 布局和人工编辑能力。
- 不改变普通章节模式的 LLM 分块契约。
- 不在本次修复中调整供应商并发数、HTTP 超时或退避算法。

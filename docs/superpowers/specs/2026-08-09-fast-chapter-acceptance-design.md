# 快速创建章节与后台参考探测设计

## 目标

缩短“创建并开始生成”的前台等待时间。LLM 完成分块并通过结构校验后，服务端立即创建章节任务并返回 `202`；IndexTTS 参考文本时长探测与修正转入后台的“参考音频”阶段。

## 现状与根因

当前创建接口在写入章节任务前，逐段串行调用 IndexTTS 生成临时参考音频并测量时长。实测单段约需十余秒，多段会把 GPU 推理时间全部叠加到 HTTP 请求中，WebUI 在此期间只能显示“正在规划分块”。此外，探测通过后正式参考任务仍会重复执行缓存发布路径，Windows 上偶发的文件占用还可能使整个创建请求返回 `500`。

## 采用方案

1. `ChapterService.submit()` 仅执行输入校验、LLM 分块和计划校验，然后持久化 queued run、启动后台协程并返回。
2. 后台 `_run()` 在每段正式 reference job 之前执行参考文本时长探测与必要的 LLM 修正。
3. 探测继续调用正式 `SynthesisService.generate_reference()`，因此使用完全相同的 cache key；探测结果一旦通过，随后的正式 reference job 直接物化缓存，不再第二次运行 IndexTTS。
4. 修正文本通过 `SegmentStore.patch_inputs()` 的 revision OCC 写回。若探测期间用户已经编辑该分块，后台不得覆盖用户内容，而是重新读取并使用最新记录。
5. 缓存命中只物化已有 blob，不再次发布同一内容 blob。
6. Windows 原子发布对短暂 `PermissionError` 做小幅、有界重试；其他错误和持续占用仍按原契约失败。

## 用户可见状态

- POST 等待期间，“文本规划”表示真正的 LLM 请求与 schema 校验。
- POST 返回后，章节立即出现在历史列表。
- 后台探测与参考生成期间，四阶段进度条进入“参考音频”。
- 探测、修正或推理失败只使已创建的章节任务进入失败状态，不再让创建接口无任务可查地返回通用 `500`。

## 数据一致性

- 不新增数据库迁移，不改变公开请求/响应 schema。
- 每个执行仍使用独立 `job_id`，缓存命中不改变版本和任务审计。
- 自动修正仅在输入 revisions 与探测开始时一致时提交。
- 发生 OCC 冲突时保留用户编辑，绝不静默覆盖。
- blob 仍以 SHA-256 寻址；已存在且哈希相同视为幂等成功，内容不同时保持冲突保护。

## 非目标

- 不将 LLM 分块本身改为异步；章节记录依赖 LLM 输出的分块结构。
- 不并行执行多段 IndexTTS；继续遵守单 GPU consumer。
- 不改变 3–10 秒 GSV 参考音频窗口。输入给 IndexTTS 的基础音色仍不受该窗口限制。

## 验收

1. 阻塞 IndexTTS 客户端时，创建接口仍能在 LLM 完成后快速返回 `202`。
2. 后台释放后章节可继续完成，单段探测通过时 IndexTTS 只调用一次。
3. 第二次相同 reference 请求命中缓存，不再次调用 blob 发布。
4. `os.replace` 首次短暂抛出 `PermissionError` 时能重试成功；持续失败仍上抛。
5. 章节创建、局部重生成、缓存冲突、任务恢复与 UI 现有回归测试全部通过。
